# Field Definition — Phase Map

## Purpose

Seat Phase Map in Field as the chamber-held relational positioning surface through which valid exhibition and conversion standing may become viewable in relation.

Phase Map does not function as passage.
Phase Map does not function as chamber identity.
Phase Map does not function as directory.
Phase Map does not function as Chamberplate.

Phase Map exists to:

- position what may be encountered in relation
- render visibility of sealed, released, dependent, or unavailable standing where permitted
- expose valid route visibility without inventing permission
- communicate unlock visibility through registered phase standing
- position registered conversion openings where permitted
- preserve relational positioning without collapsing into local readability or authority

## Native Position

Within native order:

- Codex holds authority
- Field structures relation
- Measures registers reveal and progression
- Chazz executes only what is already defined

Phase Map belongs to Field as a chamber-held relational positioning surface.

It resolves as:

- relational positioning surface
- encounter visibility surface
- registered route-visibility surface
- unlock-visibility communication surface
- exhibition / conversion positioning surface

It is not:

- Codex authority
- Measures registry
- Harrumuk Passage
- Obsidian Chamber itself
- Obsidian Directory
- Chamberplate
- Legacy seating

## Start Standing

Phase Map may be encountered only after valid chamber entry standing exists and chamber-held positioning visibility is permitted.

Valid Phase Map availability may occur only when:

- Obsidian Chamber standing is available
- chamber-held surface visibility is permitted
- registered local standing allows relational positioning visibility
- Phase Calendar / release / state / cadence standing permit current visibility
- NotChazz does not block access

Premature visibility is not valid phase-map standing.

## Structural Role

Phase Map resolves as:

- phase-map surface
- relational positioning surface
- visibility surface
- registered route-visibility surface
- unlock-visibility surface
- exhibition / conversion positioning surface

## Required Relations

Phase Map must structurally relate:

- Obsidian Chamber as chamber-held host surface
- Obsidian Directory as prior or adjacent chamber-local readability surface where applicable
- Chamberplate as distinct chamber-held exhibition surface
- Measures-registered local units as positionable only where permitted
- registered conversion openings such as SRC uploads, completion fields, educational fields, or other conversion fields where permitted
- Phase Calendar as release and cadence-bearing condition set
- Phase Release as reveal permission condition
- Phase State as present reveal standing
- cadence as registered progression condition where applicable
- dependency standing as registered condition
- NotChazz as boundary-preserving constraint intelligence

Phase Map does not originate those relations.
It positions them where valid visibility exists.

## Identity Rule

Identity in Phase Map resolves through:

- relational position
- registered visibility standing
- registered dependency standing
- chamber-held relation

Phase Map is not identified by chamber identity, directory readability, decorative layout, or Chamberplate symbolism.

Epithet may appear only where already seated through valid relation.
Slug is never authority.

## Required Field States

Phase Map must be able to express:

- unavailable
- held
- sealed
- dependent
- visible
- positioned
- route_visible
- unlock_visible

These are relational positioning states.
They do not replace chamber states, directory readability states, or authority conditions.

## Dependency Rule

Relational positioning visibility in Phase Map depends on relation to:

- valid chamber-held host standing
- valid registered local unit standing
- valid Phase Calendar / release / state / cadence standing
- valid dependency standing
- boundary validity under NotChazz

If required relation is absent, Phase Map may show unavailable, held, sealed, or dependent standing.
It may not invent visible, route_visible, or unlock_visible standing.

## OAR Relation

OAR1 does not originate in Phase Map.
OAR2 does not originate in Phase Map.

Phase Map may be OAR-addressable as a visibility or positioning surface when meaningful access or route standing is encountered, but it does not create passage, truth, or Legacy.

## Transition Rule

Phase Map may position visibility toward:

- valid chamber-held exhibition surfaces
- valid chamber-local continuance
- valid conversion openings where Measures permits them
- valid downstream routes where Measures permits them

Phase Map may show route visibility and unlock visibility, but visibility is not permission by itself.

No direct transition is valid from Phase Map to:

- Codex
- Legacy
- authority override
- unregistered surfaces
- false-open routes

Phase Map positions.
It does not authorize.

## Chamber Relation

Obsidian Chamber holds Phase Map as a chamber-held surface.

Obsidian Directory resolves chamber-local readability before or alongside valid positioning visibility where applicable.

Chamberplate remains a distinct chamber-held exhibition surface and carries the seven gates representation.

Phase Calendar, Phase Release, Phase State, and cadence govern what may be visible and when.

Chamber is seating and holding.
Directory is readability.
Phase Map is relation-at-view.
Chamberplate is exhibition surface.

These may correspond.
They may not collapse.

## Boundary Rule

Phase Map may:

- position valid registered units in relation
- communicate sealed, dependent, or visible standing
- communicate unlock visibility where permitted
- expose valid route visibility
- expose valid conversion openings where permitted
- preserve relational clarity for exhibition and conversion

Phase Map may not:

- replace chamber identity
- replace directory readability
- replace Chamberplate
- invent release
- invent cadence
- bypass Measures
- bypass NotChazz
- substitute visual arrangement for registered standing

## Correction Rule

When relational positioning is incomplete, unreleased, or cadence-bound:

- phase-map visibility remains bounded to actual standing
- sealed, held, or dependent visibility remains preserved
- no false-open route is rendered
- no false unlock visibility is rendered
- no false conversion opening is rendered
- correction resolves upstream at registration, dependency, release, cadence, or access layer

No cosmetic map visibility counts as valid route.

## Validation Rule

Phase Map is valid only when it can structurally express:

- relational positioning distinct from chamber identity
- visibility distinct from permission
- route visibility distinct from route authorization
- sealed, dependent, visible, and unlock-visible distinctions
- chamber-held phase standing without authority drift
- Chamberplate and Directory as distinct but related surfaces
- registered conversion openings only where permitted by Measures

## End Standing

Phase Map resolves successfully when relational standing is either:

- correctly held
- correctly sealed
- correctly dependent
- correctly visible
- correctly positioned
- correctly showing valid route visibility
- correctly showing unlock visibility where permitted
- correctly showing registered conversion openings where permitted

Success does not mean everything is open.
Success means relational visibility is accurate without drift.

## Success Condition

Phase Map is properly seated in Field when it can hold chamber-related relational positioning, route visibility, unlock visibility, and registered conversion openings for exhibition and conversion without collapsing into:

- passage
- chamber
- directory
- Chamberplate
- authority
- frontend invention

Codex holds.
Field structures.
Measures registers.
Chazz executes.
