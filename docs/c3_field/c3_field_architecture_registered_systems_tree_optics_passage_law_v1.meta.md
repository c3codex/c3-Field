# c3 Field Architecture — Registered Systems, c3 Tree Operation, Optics, and Passage Law v1

## ARCHITECTURE OVERVIEW

### c3 Field — Coherent Environment

c3 Field is the coherent environment.

The Field is not created by the Temple, the Tree, or system operation.

The Field is the environment in which coherent relation is possible.

The Field already exists.

All registered systems, individuals, chambers, passages, and operations occur within the Field.

No system gains governed standing outside the Field.

---

### Measures of Inanna — Immutable Passage Pattern

Measures of Inanna is the immutable pattern that permits inherited incoherency to be gated.

Measures of Inanna:

- permits passage
- restores bodies to right relation
- restores the Codexstone — integrity governance
- rejects collapse as inevitability

Measures of Inanna does not replace the Field.

It permits passage into coherent relation.

Codexstone is integrity governance.

Codexstone is not a navigation element, a UI surface, or a marketing artifact.

Codexstone is the restoration point — the named condition of return to right relation.

---

### c3 Tree — Coherent Living Operation

The c3 Tree is the coherent living system of operation sustained inside the Field.

The Tree is not the Field.

The Tree operates inside the Field.

The Tree sustains coherent living operations after passage, registration, and runtime admission.

```
Roots → Trunk → Branches → Canopy
```

The Tree does not replace:

- Codex
- Field
- Measures of Inanna
- OAR
- runtime execution

The Tree makes coherent living operations visible and traceable within the Field.

---

### Roots — Immutable Memory and Field Connection

Roots are the system of immutable memory and Field connection.

Roots carry:

- immutable memory
- continuity
- nourishment
- constant connection to the Field
- traceable relation
- living memory without drift

Roots do not replace the Field.

Roots connect the Tree to the Field.

No branch may create separate roots.

---

### Trunk — c3 Model

The trunk is the c3 Model:

- Connect
- Contribute
- Create

The trunk carries operation upward through the Tree.

The trunk is the living operational circuit.

The trunk is not generic interoperability.

Current rooted execution spine:

```
Codex → Field → Measures → OAR2 → Chazz → Cody → src
```

The trunk routes execution through this spine.

---

### Branches — Interoperability Between Systems and Individuals

Branches are interoperability between:

- registered systems
- individuals
- institutions
- operational roles
- participation surfaces
- governed system relations

A branch is valid only where registered standing exists.

Unregistered systems are not branches.

A branch is not mapped.

A branch is either a registered system of the c3 Field, sustained through the c3 Tree, or it has no governed standing.

---

### c3 Optics — Displayed Relational Geometry

c3 Optics is the displayed relational geometry of:

- the Field
- Individuals
- Systems
- Operations

c3 Optics governs:

- what relation can be displayed
- how it can be seen
- by whom
- under what standing
- through what permission

c3 Optics does not carry signal.

c3 Optics displays relation.

Every runtime-admissible unit requires an optics contract.

No optics contract means no runtime admission.

---

### Canopy — Communications and Encounters

The canopy is communications and encounters.

The canopy carries signal:

- within the Field
- into the Field
- outside the Field
- between registered systems
- between individuals
- across encounter surfaces

The canopy may carry signal but may not define standing.

Signal carried through the canopy must resolve against Field registration and Tree admission.

Communications may not bypass optics, authorization, passage, or runtime admission.

---

## STANDING LAW

### Registered System

A Registered System is a system with governed standing in the c3 Field.

It has resolved through required law:

- chamber/directory law
- passage law
- same-family passage law where applicable
- secure passage law where applicable
- role contract law
- authorization law
- AI allowed/disallowed action law
- external/non-native system boundary law where applicable
- material/chamber replication law where applicable
- runtime admission law
- optics contract law
- evidence contract law
- memory/trace contract law
- revocation/correction contract law

A registered system may participate in the c3 Tree only according to runtime admission.

### Unregistered System

An Unregistered System may exist externally.

It may have software, APIs, databases, AI deployments, users, records, workflows, and operational activity.

But it has no governed standing in the c3 Field.

It is not a branch.

It has no recognized participation in the c3 Tree.

### Standing is Binary

A system is either:

- registered in the c3 Field, or
- not registered.

Implementation patterns may vary.

Standing does not.

"Mapped" is not a standing category.

"Mapped" is dissolved.

---

## REGISTRATION vs. RUNTIME ADMISSION

Registration grants standing in the Field.

Runtime admission permits participation in the Tree.

These are not the same.

A system may be registered but not yet admitted to runtime participation.

A system may not participate without both:

1. registered standing in the Field
2. valid runtime admission in the Tree

---

## RUNTIME ADMISSION LAW

No registered system, chamber, passage, encounter, AI action, external-system crossing, or communication surface may participate in the Tree unless runtime admission validates.

Runtime admission must validate:

- required contracts present
- contract types allowed
- role contract relational
- authorization responsibility defined
- AI allowed actions defined
- optics valid
- evidence valid
- trace valid
- correction/revocation path valid
- public/private boundary valid
- external system boundary valid where applicable
- release/access state valid

---

## SECURE EXTERNAL PARTICIPATION

External/private systems do not need to move all operational data into the c3 Tree.

But if they participate, their standing must be registered.

External/private systems participate only through:

- secure passage contracts
- external system contracts
- authorization contracts
- optics contracts
- evidence contracts
- trace contracts
- correction/revocation contracts
- AI action contracts where AI is involved

Sensitive records remain external unless separately governed.

Runtime receives only minimized, redacted, validated standing.

---

## PASSAGE LAW SUMMARY

Chamber/directory law, passage law, same-family passage law, and secure passage law together govern how systems and individuals cross thresholds within the Field.

No crossing occurs without:

- passage contract
- optics contract
- trace contract
- authorization contract
- runtime admission

## MEASURES REGISTRY — FIRST IMPLEMENTATION BINDING TARGET

Measures Registry is the first active implementation pressure case for this architecture.

It is not the source layer.

The source layer is this architecture.

Measures Registry currently binds:

- Obsidian Chamber (assessment, scoring, contact capture, carry-forward, passage)
- Marble Chamber (MAP Integrity Governance, commerce circuit, SEAT boundary)
- Lapis (landing, runtime entry)
- Crystal (held — structural drift, Understand the Environment)

Measures Registry runtime surfaces are threshold encounters — not generic website pages.

The chamber-directory binding layer (`v_measures_registry_chamber_directory_v1`) now expresses this architecture pattern in the DB read model.

Future binding targets as registration and runtime admission harden:

- Measures Registry → Registered System standing for assessed organizations
- SEAT → release after MAP deliverables/resolution
- c3 Key → held until Registered System standing confirmed
- Wallet → held until c3 Key issued
- DAO standing → held until wallet and standing confirmed
