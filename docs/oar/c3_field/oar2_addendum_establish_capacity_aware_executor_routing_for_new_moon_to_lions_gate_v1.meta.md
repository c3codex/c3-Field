# OAR2 Addendum — Establish Capacity-Aware Executor Routing

## PURPOSE

Establish capacity-aware executor routing for the New Moon to Lion’s Gate Priority Initiative.

This addendum preserves equal advisement standing while assigning workload according to demonstrated execution endurance, continuity requirements, task size, and closure risk.

Equal advisement standing does not require symmetrical workload assignment.

## OBSERVED

The initiative requires sustained work across:

- Codex discovery;
- database migrations;
- registry reconciliation;
- artwork registration;
- Phase Calendar recovery;
- process registration;
- dashboard read models;
- FREE admission;
- parallel runtime verification;
- deployment preparation;
- cutover and rollback validation.

Cody can perform strong source execution, inspection, validation, and bounded implementation work.

Cody also reaches execution degradation or poodlegation earlier during long, multi-stage work.

Claude is better positioned to retain continuity across heavier database, registry, migration, runtime, and multi-stage execution chains.

The current initiative-registration OAR was shared with both executors.

Claude returned migration advisement and authorization.

Cody became the mutation executor and began the OAR1.

That bounded execution may complete as routed.

It does not establish the default workload allocation for the remaining initiative.

## ALIGNED

This addendum preserves:

- operator authority;
- dual executor advisement;
- role-bound AI execution;
- one mutation executor per bounded OAR2;
- exact evidence attribution;
- independent validation;
- OAR2-to-OAR1 closure;
- branch autonomy;
- fail-closed execution;
- capacity-aware routing.

Capacity affects assignment.

Capacity does not alter authority standing.

## SINGLE-MUTATION-EXECUTOR RULE

Each bounded OAR2 must name exactly one primary mutation executor.

The same OAR2 may name additional:

- advisors;
- reviewers;
- validators;
- evidence-return roles.

Additional roles do not receive mutation authority unless the OAR2 defines non-overlapping mutation surfaces explicitly.

Sending one OAR2 path to multiple roles means review and advisement unless the file assigns mutation authority to each role separately.

Receipt is not mutation authority.

## NON-OVERLAPPING WORK RULE

Parallel work is permitted only when:

- each surface is explicitly named;
- each executor has a separate bounded assignment;
- database objects do not overlap;
- source files do not overlap;
- evidence responsibilities are distinct;
- integration order is defined;
- rollback ownership is defined.

If overlap is discovered:

- stop the later mutation;
- preserve evidence;
- route the conflict to Chazz;
- return the decision to op044.

## CAPACITY-AWARE ASSIGNMENT TEST

Before routing an OAR2, determine:

1. expected duration;
2. number of dependent stages;
3. database mutation scope;
4. source mutation scope;
5. cross-system continuity requirement;
6. rollback complexity;
7. evidence volume;
8. likelihood of executor degradation before closure.

Route to Claude by default when work is:

- long-running;
- multi-stage;
- database-heavy;
- migration-heavy;
- registry-wide;
- dependency-sensitive;
- continuity-sensitive;
- critical-path work.

Route to Cody when work is:

- bounded;
- discrete;
- independently testable;
- source-focused;
- validation-focused;
- review-focused;
- low-overlap;
- safely closable within one execution chain.
