# Measures Registry Dev Shell Isolation Boundary v1

## Isolation Rule

The dev shell is the minimum current runtime frame required to resolve registry state, render governed absence, preserve navigation continuity, and dispatch shell-level surfaces. Artifacts are not part of the active dev shell merely because they are referenced by it, share a Measures Registry filename, or exist inside a current source file.

Upstream trace remains outside the shell. Downstream authority remains held outside the shell. Mixed files are classified as operator-review conflicts because read-only classification cannot safely split them.

## Operator-Review Conflicts

### Conflict 1 — Mixed Registered Orchestrator

`src/measures_registry/registered_runtime/MeasuresRegistryRuntimeRegistered.tsx` is the current shell orchestrator, but it also contains:

- assessment scoring and durable capture insertion
- publication registry and dispatch queries
- publication subscription insertion
- MAP commerce-contract queries
- MAP checkout creation and payment-return verification

The shell role is current; the embedded downstream roles remain unproven. Whole-file admission into an isolated dev shell would cause authority bleed.

### Conflict 2 — Assessment Renderer Boundary

`RegisteredPublicAssessment.tsx` is an active renderer, while assessment/scoring authority remains unproven in the launch-authority gap matrix. Determine whether the dev shell retains only a held boundary renderer or whether assessment belongs entirely downstream.

### Conflict 3 — Publication Renderer Boundary

`RegisteredStructuralDrift.tsx` renders publication content and exposes subscription capture while Paragraph/publication authority remains unproven. Public route-shell existence does not resolve publication authority.

### Conflict 4 — MAP and Payment Renderer Boundary

`MarbleCommerceDirectory.tsx` renders MAP circuits, payment confirmation, payment CTA behavior, and SEAT language while MAP, payment, Stripe, and SEAT authority remain unproven. It cannot be classified as clean shell code.

### Conflict 5 — Provider Ownership

The storage-provider OAR1 records an implemented live schema contract, while the Batch 1 seat/register review classifies the representative provider closeout as protected Measures of Inanna material and the launch gap records integration authority as unproven. Operator must resolve system ownership separately from implementation fact.

### Conflict 6 — Circuit Contract Wording

Marble circuit documents use `status: seated` and define runtime anchors, while the seat/register review protects representative records under shared governance and the launch gap records MAP/payment/SEAT authority as unproven. `seated` contract wording must not be interpreted as active domain authority without an explicit standing reconciliation.
