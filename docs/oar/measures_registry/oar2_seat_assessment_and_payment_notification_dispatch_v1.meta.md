# OAR2 — Seat Assessment and Payment Notification Dispatch

## OBSERVED

Measures Registry now has explicit seat-hold notification dispatch standing.

Assessment completion and MAP payment events still need governed notification dispatch.

Current operational gap:

- an institution may complete an assessment without immediate operator notification
- a MAP payment may complete without explicit operator notification
- participant confirmation should be governed and traceable where appropriate
- notification copy must not be authored by frontend
- notification delivery must not imply SEAT standing, Registry Certification, c3 Key issuance, conversion, or public recognition

This is an operational notification seam.

## ALIGNED

Notification provider is transport only.

Notification authority must remain DB-seated.

Frontend may not author email copy.

Dispatch must be append-only, traceable, and bounded to verified events.

Authority order remains:

Codex -> Field -> Measures -> OAR2 -> Chazz -> Cody -> src

Notification order:

event verified
-> DB template resolved
-> dispatch function invoked
-> provider transports
-> dispatch log records outcome
-> operator/participant receives governed notice

## ROUTED

Seat governed notification dispatch for assessment completion and MAP payment events.

### 1. Event types

Seat notification handling for:

- assessment_completed
- map_payment_completed
- map_payment_failed
- map_payment_canceled

### 2. Recipient classes

Supported recipient classes:

- operator
- participant

Required dispatches:

assessment_completed:

- operator notification required
- participant confirmation optional, but if implemented must use DB-seated template

map_payment_completed:

- operator notification required
- participant receipt/confirmation required if payment success is confirmed

map_payment_failed:

- operator notification optional but logged
- participant notification optional only if provider/payment flow already supports safe confirmation

map_payment_canceled:

- operator notification optional but logged
- participant notification optional only if safe and non-confusing

### 3. DB templates

Create DB-seated templates for each supported dispatch.

Suggested table:

- measures_notification_template

Minimum fields:

- template_key
- event_type
- recipient_class
- subject
- body
- is_active
- created_at
- updated_at

Templates must not include:

- certification claim
- conversion claim
- SEAT standing claim
- c3 Key claim
- DAO standing claim
- payment link except where explicitly generated by payment flow
- marketing enrollment language

### 4. Dispatch log

Create append-only dispatch log.

Suggested table:

- measures_notification_dispatch_log

Minimum fields:

- id
- event_type
- recipient_class
- source_table
- source_id
- recipient_email
- template_key
- provider
- provider_message_id
- dispatch_state
- error_message
- created_at

Allowed dispatch_state values:

- attempted
- sent
- failed
- skipped
- blocked

Do not overwrite dispatch history.

### 5. Assessment notification

When an assessment completion record is confirmed, operator notification should include governed data where available:

- capture_id
- institution/company
- contact name
- contact email
- business type
- assessment score
- recommended pathway
- structural drift / risk standing if seated
- submitted_at
- admin/review reference if available

Participant confirmation, if enabled, should include:

- assessment received
- recommended pathway prepared
- no certification/SEAT/c3 Key claim
- next step language only where seated

### 6. Payment notification

When MAP payment success is confirmed, operator notification should include governed data where available:

- payment/session id
- capture_id or assessment reference if linked
- participant email
- selected pathway
- pathway price
- payment state
- Stripe/payment provider reference
- completed_at

Participant confirmation should include:

- payment received
- selected MAP pathway
- receipt expectation
- next step expectation
- no SEAT/certification/conversion/c3 Key claim

Payment failed/canceled events should be logged and may notify operator.

### 7. Provider transport

Preferred provider:

- Resend

Use existing environment variables where available.

Do not expose secrets.

Provider transport must be server-side only.

No frontend send.

### 8. Trigger boundary

Do not rely on React/client-only dispatch.

Allowed trigger points:

- serverless function after assessment insert confirmation
- database function invoked from controlled server path
- Stripe webhook/payment success handler after verified provider event
- operator-controlled retry where state permits

Do not create public unauthenticated dispatch endpoints.

### 9. Idempotency

Prevent duplicate sends.

Use event_type + recipient_class + source_id + template_key or equivalent idempotency key.

Repeated attempts may be logged, but duplicate successful sends must be blocked unless explicitly retried by operator.

### 10. Operator review

If an admin/operator review surface exists, it may show:

- notification status
- last attempted_at
- last sent_at
- failed reason
- retry action where safe

It may not show provider secrets.

### 11. Build and validation

Validate:

- assessment_completed operator dispatch succeeds
- assessment participant confirmation is either implemented or explicitly held
- map_payment_completed operator dispatch succeeds
- map_payment_completed participant confirmation succeeds
- failed/canceled events log correctly
- duplicate successful dispatch is blocked
- provider failure logs failed state
- no payment/MAP/assessment logic is altered
- build passes

## CODY ROLE

Cody may:

- inspect existing assessment capture and MAP payment flow
- inspect existing seat-hold notification dispatch system
- reuse or generalize notification templates/logs where structurally clean
- create DB templates and append-only dispatch log
- add server-side provider dispatch through Resend
- wire controlled dispatch after verified assessment/payment events
- add idempotency protections
- update operator review status where available
- write OAR1 with validation evidence

Cody may not:

- send email from frontend
- hardcode email copy in frontend
- expose public dispatch access
- expose secrets
- create automatic marketing enrollment
- add certification/conversion/SEAT/c3 Key claims
- alter Stripe payment logic beyond notification hook
- alter MAP logic
- alter assessment scoring logic
- batch send historical records without explicit separate OAR

## VALIDATION

This OAR resolves when:

- notification templates are DB-seated
- dispatch log is append-only
- assessment completion notification works or held reason is documented
- MAP payment notification works or held reason is documented
- provider transport is server-side
- idempotency prevents duplicate successful sends
- constraints are preserved
- build passes
- OAR1 is written beside this OAR2
