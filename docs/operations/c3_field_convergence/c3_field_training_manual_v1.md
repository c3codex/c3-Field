# c3 Field Training Manual
## Version 1

## Purpose

This manual teaches a new Operator, Cody, Chazz, or registered operational role how to participate in the c3 Field Convergence operational spine.

It is training material only. It does not grant authority.

## What c3 Field Is

c3 Field is an operational governance initiative.

It proves that coherent work can move through:

- source authority
- role distinction
- registered process
- bounded execution
- validation
- append-only memory
- correction lineage

without collapsing into informal thread drift or simulated continuity.

## Native Stack

The native stack is:

```txt
Codex -> Field -> Measures -> Chazz -> Cody -> src
```

Remember:

- Codex holds.
- Field structures.
- Measures registers.
- Chazz routes and validates.
- Cody executes.
- src renders.

## The 21 Of Coherence

The 21 of Coherence consists of:

- the 7 Constraints
- the 7 Agreements
- the 7 Resolutions of Coherence

Training rule:

If an action violates role distinction, verification, native order, or coherence, it must be held or corrected.

## How To Read An OAR2

Read an OAR2 in this order:

1. `document_scope`
2. `status`
3. `expected_oar1`
4. `OBSERVED`
5. `ALIGNED`
6. `ROUTED`
7. `NOT AUTHORIZED`
8. `VALIDATION`

Do not execute from the title alone.

Do not execute from chat instruction alone if it conflicts with OAR2 boundaries.

## How Cody Executes

Cody executes only from seated authority.

Cody should ask:

- What is the source OAR2?
- What is the expected OAR1?
- What is authorized?
- What is explicitly not authorized?
- What evidence must be returned?
- What standing should remain external to Cody?

Cody must stop if authority is missing or ambiguous.

## How Chazz Validates

Chazz validates:

- architecture
- role boundary
- source alignment
- correction need
- coherence
- whether standing can advance

Chazz validation remains external to Cody execution.

## How Held States Work

Held states protect coherence.

Common examples:

- `held_pending_operator`: Operator decision required.
- `held_pending_source`: source authority missing.
- `held_pending_validation`: Chazz validation required.
- `held_pending_deployment`: deployment condition not met.
- `held_pending_correction_oar2`: correction route required.

Held is not failure.

Held is truth preserved under pressure.

## How Correction Cycles Work

Correction cycles retain prior evidence.

A correction cycle should preserve:

- original OAR2
- attempted OAR1
- validation finding
- correction OAR2
- final OAR1

Never erase the mistaken or partial path.

## How To Verify Registry Standing

To verify operational standing:

1. Check the process instance.
2. Check transition events.
3. Check seeded reference standing.
4. Confirm held or correction fields.
5. Confirm the frontend is reading registry-backed state.
6. Confirm append-only records were not mutated.

If registry state is missing, the correct frontend state is held.

## Example Walkthrough: Valid OAR Cycle

1. Operator confirms OAR2.
2. Process enters queue.
3. Cody executes bounded task.
4. Cody writes OAR1 evidence.
5. Transition log records execution.
6. Chazz reviews.
7. Chazz validates or routes correction.
8. Closeout records final standing.

## Example Walkthrough: Held OAR Cycle

1. OAR2 is routed.
2. Cody detects missing authority.
3. Process enters held state.
4. OAR1 records held evidence.
5. Operator or Chazz resolves condition.
6. New transition event records release or correction.

## Example Walkthrough: Correction Cycle

1. Cody executes from OAR2.
2. Chazz finds drift.
3. OAR1 remains as partial evidence.
4. Correction OAR2 is created.
5. Correction scope is bounded.
6. Cody executes correction.
7. Chazz validates correction.
8. Transition log preserves full lineage.

## Common Mistakes

Avoid:

- treating a proposed OAR2 as confirmed
- skipping OAR1 evidence
- letting Cody validate itself
- treating deployment as validation
- deleting failed evidence
- using recovered intel as authority before incorporation
- hardcoding runtime truth that belongs in registry
- expanding scope during refinement

## Practice Exercises

Exercise 1:

Given a proposed OAR2 with no expected OAR1, identify why execution must hold.

Exercise 2:

Given a completed Cody implementation with no Chazz validation, identify the correct validation standing.

Exercise 3:

Given recovered thread intel that appears useful but lacks source standing, create a recovery packet and route it to Chazz.

Exercise 4:

Given a transition event with incorrect notes, explain why the original event must not be edited and what correction event should be appended.
