# CoherentAI System Map
**c3 Field / CoherentAI / Measures Installation Doctrine**

## Purpose

This document formalizes the operating structure of **c3 Field** and the role of **CoherentAI** within it.

It exists to prevent drift during installation, development, and governance execution.

This file is binding architecture for:
- request routing
- authority resolution
- anti-drift enforcement
- OAR trace design
- Measures installation processing
- future CoherentAI expansion

---

## 1. System Identity

**c3 Field** functions as a coherence-based operating system for cultural, civic, installation, and governance execution.

It is composed of:

- a **canonical data layer**
- a **canonical storage layer**
- a **stable render layer**
- a **governed execution layer**
- a **decision and anti-drift layer**
- a **trace layer**
- a **symbolic movement layer**

The system is not a marketplace, not a loose content site, and not an unbounded AI assistant surface.

It is a structured operating environment.

The civic operating model of c3 Field is:


Connect → Contribute → Create

gallery systems

3. Operational Trace Logic

All meaningful execution should be interpretable through:

Objective → Action → Result
Objective

What the task intends to stabilize, reveal, resolve, or transform.

Action

What the system actually does, through what authority layer, using what path.

Result

What changed, what redirected, what was blocked, and what became real.

This is the execution trace layer.

4. State Logic

All meaningful system movement should also be interpretable through:

Orientation → Alignment → Realization
Orientation

Recognition, visibility, encounter, placement.

Alignment

Correct relation between data, authority, and purpose.

Realization

Stable form made operational.

This is the state transition layer.

pass a governed execution envelope to the engine

Dispatcher routes through policy.

It includes:

status

authority view

forbidden paths

reason

The execution engine must receive the contract with the request.

The execution engine must never act on raw request alone.

16. SQL Governance Modes

SQL execution aligns with c3 civic structure.

CONNECT mode     → Read
CONTRIBUTE mode  → Write
CREATE mode      → Migrate
CONNECT / Read

Allowed:

SELECT

inspection

indexing

validation

No state change.

CONTRIBUTE / Write

Allowed:

INSERT

UPDATE

UPSERT

Used for:

logs

queue entries

categorized runtime records

state updates

No schema mutation.

CREATE / Migrate

Allowed:

CREATE

ALTER

governed migration actions

Used for:

tables

views

schema evolution

This mode requires explicit authority.

17. SQL Adapter Law

CoherentAI must not run direct ungoverned SQL.

All SQL should pass through a controlled execution layer that can enforce:

mode

scope

table/view access

migration restriction

logging

CoherentAI is a scribe with governed execution, not a roaming database administrator.

21. MEs Requirement

Because MEs are governance-bearing forms, any CoherentAI task involving an ME should produce:

a guard event

an OAR log

22. Measures Runtime Media Law

Operational Measures assets resolve through:

measures_media

v_measures_media_resolved

They do not resolve through:

canon_artifact

pasted public URLs

deleted local registries

This is a binding anti-drift decision.

23. Component Authority Law

Presentation components must not directly resolve canonical authority.

Components may:

render props

render hook outputs

render resolved data

Components may not:

invent storage paths

paste source URLs

bypass resolved views

act as source-of-truth resolvers

Resolver logic belongs in:

hooks

loaders

governed data access layers

24. Same-Pillar Import Law

Within a pillar:

prefer relative imports for same-pillar files

Do not treat same-pillar access as cross-pillar dependency when it is local structural work.

This prevents false drift and preserves pillar cohesion.
